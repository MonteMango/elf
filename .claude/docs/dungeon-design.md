# Дизайн подземелий (Dungeons)

> **Статус:** ранний дизайн. Базовые решения зафиксированы, детали реализации будут уточняться по мере написания кода. Created by Vitalii Lytvynov.

---

## Обзор

**Подземелье (Dungeon)** — структурированное многокомнатное приключение, доступное только в **Dungeon Day** (см. `game-design.md` → *Day Types*). Игрок входит в подземелье отрядом из **5 эльфов** (главный герой + 4 случайных эльфа из дома), проходит граф комнат, сражается с монстрами и финальным боссом.

Подземелья — **статический контент**: их структура, монстры в комнатах и параметры специальных событий описаны в `Resources/Dungeons.json`. Состояние конкретного прохождения (живы/мертвы, текущий HP, какая комната пройдена) живёт в save-данных и ссылается на статический контент по `UUID` (см. `persistence-patterns.md` → *ID-Reference Pattern*).

## Поток игрока

День помечается как Dungeon Day через существующую систему календаря: `DayType.dungeon` (см. `DefaultCalendarService` и `DayType.swift`). На таких днях `ActionType.dungeon` — единственное доступное действие.

### Шаги

1. **`GameDayScreen`** в Dungeon Day показывает **единственную кнопку — `Dungeon`**. Все остальные действия (охота, рыбалка и т.д.) недоступны.
2. По тапу:
   - Из пула доступных подземелий случайно выбирается одно (на MVP — единственное).
   - Из дома игрока случайно выбираются 4 эльфа в команду к главному герою.
3. Открывается **`DungeonOverviewScreen`** с сегмент-контролом и **статичной кнопкой `Entrance` снизу** (видна на всех вкладках):
   - **Overview** *(по умолчанию)* — короткое описание, монстры, боссы, возможный дроп подземелья.
   - **Squad** — главный герой + 4 случайных эльфа (только информация, не выбор).
   - **Map** — визуализация графа комнат от входа до босса.
4. Тап по `Entrance` запускает поход. Открывается **`DungeonRoomScreen`** — структура та же (сегмент-контрол + статичная кнопка снизу), но контекст уже **конкретной комнаты**:
   - **Overview** — заголовок и описание комнаты, монстры в ней.
   - **Squad** — текущий состав группы (живые/мёртвые после предыдущих комнат).
   - **Map** — позиция группы на карте подземелья.
   - Статичная кнопка снизу: **`Fight`** (для combat / miniBoss / boss комнат) или соответствующая action-кнопка для special event (например, `Drink`/`Open`).
5. По тапу `Fight` — стартует битва: 5 эльфов слева, монстры комнаты справа (стандартный `BattleService` + `BattleScreen`).
6. После победы открывается стандартный экран результатов битвы, затем — **`DungeonRoomScreen` для следующей комнаты** (с применённым восстановлением 25% HP/MP, см. ниже).
7. После победы над финальным боссом подземелье помечается как пройденное на текущий Dungeon Day. Игрок возвращается на `GameDayScreen`, откуда переходит к следующему дню обычной кнопкой `Next Day`.

### Лимиты на день

- За один Dungeon Day игрок может пройти **только одно** подземелье. Кнопки выхода из подземелья **нет** — поход идёт до победы или до смерти героя.
- Доступное подземелье выбирается **рандомно** из пула при тапе по кнопке `Dungeon`.
- На MVP в игре **одно** подземелье.

## Типы подземелий

Поле `type` — это в первую очередь подсказка для UI и для контент-авторов. Реальная логика прохождения определяется **самим графом комнат** (поле `nextRoomIds`).

### `onePath` — линейный путь

```
[R1] → [R2] → [R3] → [R4 (босс)]
```

Простейший случай. Отряд из 5 эльфов проходит комнаты последовательно. MVP-цель.

### `splitPath` — расщепление и слияние

```
[R1] → [R2] → ┬─ [R3] ─┬→ [R5] → [R6 (босс)]
              └─ [R4] ─┘
```

В точке расщепления отряд **случайным событием** делится на две группы (например: «эльфы переходят мост, но порыв ветра сбрасывает двоих в подземную реку»). Распределение **рандомное**: 2 эльфа уходят в одну ветку, 3 — в другую. В какую ветку попадает **главный герой** — тоже рандом.

**Параллельные бои.** В точке расщепления одна группа сражается **с UI** (та, в которой главный герой), вторая группа — **симулируется молча** на cooperative thread pool, без UI. Когда обе группы дошли до точки слияния, группы воссоединяются (с теми, кто выжил), и поход продолжается одним отрядом.

> Подробнее о симуляции «тихого» боя — раздел *Параллельные бои* ниже.

### `randomPath` — телепортация и встречи

```
Stage 1 (16 комнат) → Stage 2 (8 комнат) → Stage 3 (4 комнаты) → Stage 4 (1 комната, босс)
```

**Лор:** при входе в подземелье эльфов **разбрасывает по разным точкам** магией подземелья. Каждый эльф пробивается к финалу в одиночку, изредка пересекаясь с союзниками. На финальной комнате все выжившие встречаются у босса.

**Механика:**
1. На старте каждый из 5 эльфов **независимо** телепортируется в одну из 16 комнат стадии 1. Возможно, что в одну комнату попадут несколько эльфов (везение) — в этом случае они проходят её вместе.
2. После клира своей комнаты эльф/группа переходит в **случайную комнату следующей стадии** (одну из 8 на стадии 2, одну из 4 на стадии 3 и т.д.). Так как комнат на каждой следующей стадии меньше — естественным образом возникают встречи между эльфами.
3. Все встретившиеся эльфы дальше идут одной группой (до следующего расщепления — расщепления здесь нет, но они снова могут оказаться в разных комнатах… на самом деле нет: после встречи они уже одна группа и переходят вместе. *На MVP считаем, что встретившиеся эльфы дальше идут вместе.*)
4. На стадии 4 — единственная комната с боссом. Все выжившие из всех групп сходятся в этой комнате и сражаются с боссом единым отрядом.

**Параллельные бои.** Та группа/эльф, в которой главный герой — играется с UI. Все остальные группы — симулируются молча. См. *Параллельные бои*.

## Состояние эльфов между комнатами и в боях

### Восстановление между комнатами

При переходе из одной комнаты в другую каждый живой эльф восстанавливает **25% от максимального HP и 25% от максимального MP**, но не больше, чем до полного значения. Значение — константа на MVP. В будущем рюкзаки/предметы смогут модифицировать этот процент.

> Формула: `new = min(max, current + max * 0.25)`
>
> Примеры (при HP_max = 100):
> - current = 80 → восстановление 25 → итог 100 (clamped).
> - current = 65 → восстановление 25 → итог 90.
> - current = 30 → восстановление 25 → итог 55.

### Гибель эльфа

- Если эльф погибает в комнате — он **выбывает из подземелья**. Дальнейшие комнаты он не проходит.
- Остальная группа продолжает поход без него.
- Если погибает **главный герой** — для игрока подземелье **завершается**. Игрок возвращается на `GameDayScreen`. Оставшиеся боты-эльфы дальше **не идут** — поход обрывается, поскольку игроку нечего наблюдать (UI завязан на героя).

### HP/MP не сбрасываются между комнатами

HP и MP **сохраняются** между комнатами (только +25% от max восстанавливается на переходе). Это значит, что специальные события вроде `healingSpring` имеют реальный смысл — без них к боссу можно прийти на низком HP.

Конкретно: если эльф закончил бой в комнате 1 с 60 HP (max = 100), на переходе восстановилось 25 → в комнату 2 он входит с 85 HP. Все накопленные значения HP/MP к началу боя в комнате N равны итогу боя в комнате N-1 + одна порция восстановления.

## Состав отряда (Squad)

- 5 эльфов: **главный герой** + **4 случайно выбранных** эльфа из дома (`House.members`, всего 10 членов).
- Игрок **не выбирает** состав. Вкладка **Squad** на DungeonOverviewScreen — это **только информация** о том, кто пошёл.

## Дроп и опыт

### Дроп

- **Только с монстров.** Используется существующая система `MonsterDrops` (`weapons` / `armor` / `materials`) и `DropService`.
- **Никаких отдельных наград за прохождение** подземелья на уровне самого подземелья. Уникальность лута достигается тем, какие монстры стоят в комнатах — через них и идёт «уникальный лут».
- Дроп с боссa — это просто `MonsterDrops` боссa, более «жирный» по содержимому. Никакой особой механики.
- **Кому идёт дроп.** Игрок получает дроп **только при победе** в конкретном бою — независимо от того, жив ли герой в момент победы. Например, если герой погиб в комнате 3, но команда добила монстров — дроп с этой комнаты идёт игроку. Если же подземелье оборвалось из-за смерти героя в незаконченном бою (поражение в комнате) — дропа за эту комнату нет; дроп с предыдущих победных комнат остаётся.

### Опыт (XP)

- XP получают **только участники конкретного боя**.
- В `splitPath` это значит: эльфы, ушедшие во вторую ветку, получают XP за свой «тихий» бой; герой и его группа — за свой.
- В `randomPath` — каждый эльф/группа получает XP только за бои в комнатах, в которых лично участвовал.
- Восстановление HP/MP, смерть и всё остальное на XP не влияют — XP зависит только от факта участия в победе.

### Состояние эльфов после подземелья

- При возврате на `GameDayScreen` HP/MP всех эльфов **восстанавливаются как после обычной битвы** (та же механика, что используется сейчас в игре).
- Погибшие в подземелье эльфы — *поведение определяется существующей системой смерти эльфов в проекте; отдельной «dungeon-specific» логики смерти не вводим.*

## Структура данных (JSON)

### Файл

`Resources/Dungeons.json` — единственный файл на старте. Если контента станет много (>10 подземелий) — разнесём.

### Схема

```jsonc
[
  {
    "id": "UUID",
    "title": "Crystal Caverns",
    "description": "Короткое описание подземелья…",
    "type": "onePath",                          // .onePath | .splitPath | .randomPath
    "world": "lowerWorld",                      // совпадает с существующим WorldType
    "entryRoomIds": ["UUID"],                   // входные точки. onePath/splitPath: [одна]; randomPath: [16 комнат stage 1]
    "rooms": [
      {
        "id": "UUID",
        "title": "Зал входа",
        "description": "…",
        "stage": 1,                             // используется только в randomPath; в остальных — null или 0
        "kind": {
          "type": "combat",
          "monsters": [
            { "monsterId": "UUID", "count": 4 }
          ]
        },
        "nextRoomIds": ["UUID"]                 // для randomPath — список всех комнат следующей стадии
      },
      {
        "id": "UUID",
        "title": "Горячий источник",
        "stage": 2,
        "kind": {
          "type": "event",
          "event": { "type": "healingSpring", "healPercent": 50 }
        },
        "nextRoomIds": ["UUID"]
      },
      {
        "id": "UUID",
        "title": "Тронный зал",
        "stage": 4,
        "kind": {
          "type": "boss",
          "monsters": [{ "monsterId": "UUID", "count": 1 }]
        },
        "nextRoomIds": []                       // пусто ⇒ финальная комната
      }
    ]
  }
]
```

### Принципы

1. **Граф, а не массив.** Связь между комнатами — через `nextRoomIds`. Координаты на 2D-карте не хранятся — Map view вычисляет layout сам, исходя из графа и `stage`.
2. **`kind` комнаты — sum-type.** Каждый вариант несёт свой payload. Новый вид комнаты = новый case в enum, а не новое опциональное поле.
3. **Монстры по ссылке, а не embed.** Комнаты ссылаются на монстров по `monsterId` из `Monsters.json`. Уровень монстра уже зашит в его айдентити (ветки `level1/2/3`).
4. **Один файл — `Dungeons.json`.** Не плодим файлы заранее.
5. **Никакого `completionReward`** на уровне подземелья. Лут — только с монстров.

### Виды комнат (`kind`)

| Тип        | Payload                                | Смысл |
|------------|----------------------------------------|-------|
| `combat`   | `[MonsterRef]`                         | Обычный бой. |
| `miniBoss` | `[MonsterRef]`                         | То же что combat, но помечено отдельно для UI/лора. |
| `boss`     | `[MonsterRef]`                         | Финальная комната подземелья. Победа ⇒ подземелье пройдено. |
| `event`    | `SpecialEvent`                         | Без боя. См. ниже. |

`MonsterRef` = `{ monsterId: UUID, count: Int }`.

### Специальные события (`SpecialEvent`)

Закрытый набор. Расширение — только добавлением нового case, без обобщённой системы скриптов.

| Событие         | Параметры                            | Эффект |
|-----------------|--------------------------------------|--------|
| `chest`         | `lootTableId: UUID`                  | Открытие сундука с гарантированным луtom. |
| `healingSpring` | `healPercent: Int`                   | Восстанавливает HP отряда. |
| `oreVein`       | `oreId: UUID, attempts: Int`         | Мини-игра: добыча руды (ссылка на `Ores.json`). |
| `fishingPond`   | `fishPoolId: UUID, attempts: Int`    | Мини-игра: рыбалка (ссылка на `Fish.json`). |
| `shrine`        | `buff: BuffId`                       | Временный бафф на оставшиеся комнаты. |
| `trap`          | `damagePercent: Int`                 | Урон по всему отряду. |

> Состав финального списка событий уточним по мере необходимости. На MVP, возможно, обойдёмся `healingSpring` + `chest`.

## Архитектура (набросок)

> Финальная структура типов и сервисов будет уточнена при реализации. Здесь — целевые ориентиры.

### Типы (`elf_Kit`)

- `Dungeon` — корневая сущность подземелья. Содержит `id`, `title`, `description`, `type: DungeonType`, `world`, `entryRoomIds`, `rooms: [DungeonRoom]`.
- `DungeonRoom` — комната. Содержит `id`, `title`, `description`, `stage`, `kind: DungeonRoomKind`, `nextRoomIds`.
- `DungeonRoomKind` — sum-type комнаты (`combat`, `miniBoss`, `boss`, `event`).
- `MonsterRef` — ссылка `monsterId` + `count`.
- `SpecialEvent` — sum-type специальных событий.
- `DungeonType` — enum (`onePath`, `splitPath`, `randomPath`).

> Граф хранится **как массив комнат + связи через `nextRoomIds`**, а не как linked list. Связный список плох тем, что не описывает ветвления и слияния — это дерево/DAG. Массив + явные ссылки — стандартный способ хранить graph-DAG в Codable.

### Per-run state

- `DungeonRunState` — изменяемое состояние конкретного прохождения.
  - `dungeonId: UUID`
  - `groups: [DungeonGroup]` — активные группы эльфов в подземелье. На старте всегда одна; при `splitPath`/`randomPath` их больше.
  - `defeatedRoomIds: Set<UUID>` — пройденные комнаты.
  - `outcome: DungeonOutcome?` — `inProgress | completed | failed`.
- `DungeonGroup` — одна группа в рамках подземелья.
  - `members: [SquadMember]` (живые + мёртвые с флагом)
  - `currentRoomId: UUID`
  - `containsHero: Bool` — есть ли в этой группе главный герой (определяет, играется ли её бой с UI).

### Сервисы

- **`DungeonRepository`** — загрузка `Dungeons.json` через `ElfDataLoader`, поиск подземелья по `UUID`. Аналог `MonsterRepository`.
- **`DungeonRunService`** *(actor)* — оркестратор прохождения:
  - выбирает следующую комнату для каждой группы,
  - для группы с героем — поднимает `BattleService` с UI,
  - для других групп — поднимает `BotBattleSimulator` (см. ниже),
  - применяет восстановление 25% HP/MP при переходах,
  - управляет splitPath/randomPath логикой (рандом распределения).
- **`BotBattleSimulator`** *(actor)* — симулирует бой без UI, на фоне. Использует те же `BattleService`-механики, но прогоняет их «с максимальной скоростью» и возвращает только итог (`SimulatedBattleResult`: оставшиеся в живых + их HP/MP + накопленный дроп).
- **`DungeonRandomizer`** — чистая логика для:
  - распределения эльфов по входным комнатам в `randomPath`,
  - выбора следующей комнаты следующей стадии в `randomPath`,
  - распределения 5 эльфов на 2/3 в `splitPath`,
  - выбора, в какую ветку идёт главный герой в `splitPath`.

### Параллельные бои

`BotBattleSimulator` запускается на cooperative thread pool через `Task { ... }` (Swift Concurrency). Никакого UI, никакой анимации, бой считается «быстро как может». Результат — снимок состояния группы после боя.

`DungeonRunService` в `splitPath` стартует:
- бой группы с героем — на главном UI-потоке (через `BattleService` + `BattleScreen`),
- бой группы без героя — `Task.detached` с `BotBattleSimulator`.

Когда **оба** боя завершены и обе группы дошли до merge-точки — `DungeonRunService` объединяет группы и продолжает поход.

> Внимание: при гибели **главного героя** в групповом бою с UI — нужно решить, продолжается ли симуляция оставшихся групп. На MVP — **продолжается тихо в фоне, игрок видит финальный экран с итогом всего отряда**.

### Экраны (`elf_iOS`)

Оба экрана используют одну и ту же визуальную структуру: **сегмент-контрол сверху + 3 вкладки (Overview/Squad/Map) + статичная action-кнопка снизу**. Различается только контекст (всё подземелье vs. конкретная комната) и текст action-кнопки.

- **`DungeonOverviewScreen`** — single-file Screen pattern (см. `project-architecture.md`).
  - Контекст: всё подземелье целиком.
  - Action-кнопка: `Entrance` → старт похода и переход к `DungeonRoomScreen` для первой комнаты.
- **`DungeonRoomScreen`** — экран текущей комнаты, повторно используемый для каждой комнаты.
  - Контекст: конкретная комната.
  - Overview tab — заголовок и описание комнаты, монстры в ней.
  - Squad tab — текущий состав группы (с пометками живой/мёртвый).
  - Map tab — позиция группы в графе подземелья.
  - Action-кнопка: `Fight` (для combat/miniBoss/boss) или action-команда события (`Drink`, `Open` и т.д.) для `event` комнат.
  - По нажатию `Fight`: открывается обычный `BattleScreen` через `BattleService`, после результата — переход к следующей комнате.
- **Для `splitPath`/`randomPath`** `DungeonRoomScreen` показывает только происходящее с группой героя. Параллельные группы — TBD по UX (см. *Открытые мелкие вопросы*).

## Что переиспользуется без изменений

- **Combat:** `BattleService` + `CombatantSnapshotBuilder`. Боевая комната = `Battle` с монстрами комнаты в `rightTeam` и живыми эльфами группы в `leftTeam`.
- **Drops:** `MonsterDrops` + `DropService` отрабатывают как обычно. После боя в подземелье дроп копится в инвентарь героя.
- **Squad:** источник эльфов — `House` игрока (10 членов → выбираем 5).

## Открытые мелкие вопросы (требуют уточнения при реализации)

- **Смерть главного героя в `splitPath`/`randomPath`:** *решено* — поход обрывается, игрок возвращается на `GameDayScreen`. Бои оставшихся ботов не симулируются (играть нечего).
- **`randomPath` встречи после стадии 1:** если на стадии 2 две независимые группы попали в одну и ту же комнату — они сражаются вместе, и потом идут одной группой? Или проходят независимо? *Текущее предложение:* встретились → стали одной группой. Подтвердить при реализации.
- **MapView для `randomPath`:** как визуализировать 16/8/4/1 комнат — пользователь ещё думает над дизайном. Для `onePath` — простой линейный ряд комнат. Для `splitPath`/`randomPath` — TBD.
- **UX параллельных боёв в `splitPath`:** показывать ли игроку индикатор «вторая группа сражается, ждём…» или скрыть это полностью? Решим при реализации.
- **Финальный список SpecialEvent:** на MVP только `healingSpring`. Остальные (`chest`, `oreVein`, `fishingPond`, `shrine`, `trap`) — добавим по мере роста контента.
- **`miniBoss` как отдельный `kind` или флаг внутри `combat`?** Решим при определении Swift-типов в шаге 2.
- **Анимации переходов между комнатами:** не реализуем на MVP. Простая смена экрана.
