## Findings

### 1. [stage-1, BLOCKING — FIXED] Cross-slot merge used a stale pre-`await` snapshot, not live state

**file:** `Packages/elf_Kit/Sources/UILayer/Dev/BattleSetup/BattleSetupViewModel.swift:178, 202-206` (pre-fix)
**AC:** AC-06 (primary), AC-02 (secondary)

The Swift-concurrency consultant and the independent reviewer both confirmed, from the real
`ElfWeaponValidator` semantics, that a weapon/shield validation Task decides its cross-slot side
effect (e.g. a two-handed weapon auto-clearing an equipped shield) using the snapshot of the *other*
slot captured before its own `await` — never re-checked against the live value at write time. Two
concrete, independently reproduced regressions, both requiring only the same "await hops off
`@MainActor`" mechanism the original bug already exploited (no weaker premise):

1. **A validly-applied weapon selection could be silently dropped to nil.** Weapon Task resolves
   first and writes a compatible one-handed weapon; a concurrently in-flight shield Task's own
   snapshot still shows the *old* two-handed weapon, so its real validator response auto-clears
   `.weapons` — and without a live re-check, that stale clear overwrites the weapon selection that
   had already, correctly, landed.
2. **A two-handed weapon and a shield could end up equipped simultaneously** — the exact invariant
   the validator exists to prevent. When the shield slot was empty in the weapon Task's own snapshot,
   `.shields` never appears in that snapshot's key set at all, so the merge loop (`Set(currentItems.keys).union(validatedItems.keys)`)
   never visits it — a shield that landed live from an independent, concurrent Task during the
   weapon's `await` survives untouched, even though the weapon just resolved to two-handed.

Both were pinned by new regression tests (`testCrossSlotSideEffect_WeaponWriteSurvivesAStaleShieldValidation`,
`testCrossSlotSideEffect_TwoHandedWeaponClearsALiveConcurrentShield`) that reproduce the exact traces
above using the real `ElfWeaponValidator`'s documented clear-by-omission/auto-clear shapes as the
release payloads.

**Fix applied:** at write time, `updateSelectedItems` now compares the live `currentState.selectedItems`
against the pre-`await` snapshot; on divergence it re-runs `weaponValidator.validateAndResolve` once
against the live state (still gated by `Task.isCancelled`) and merges that result instead, using the
live state as the merge baseline. A single re-check, not a loop — the residual this leaves (a *third*
concurrent write landing in the second, much shorter await) is the same order of magnitude as the
original single-`await` race this feature already accepts. `ADR-0001`'s Neutral consequence and
`sad.md` §11's matching debt row are both updated to record this as resolved, not accepted debt.

### 2. [stage-2, non-blocking — FIXED] AC-06 regression test never exercised a colliding key

**file:** `Packages/elf_Kit/Tests/elf_KitTests/UILayer/Dev/BattleSetup/BattleSetupViewModelTests.swift:206-227`
**AC:** AC-06

`testCrossSlotRapidSelection_BothOutcomesArePreserved` only ever released disjoint validator-result
keys (`.weapons` / `.shields` never overlapping), so the per-key merge guard was never exercised on a
key two in-flight calls both write — precisely the scenario finding 1 needed to reproduce. Non-
tautological (it does fail under a full-dict overwrite) but insufficient on its own.

**Fix applied:** the two new tests in finding 1 close this gap directly; the pre-existing test was
also updated to release the extra live-re-check call the finding-1 fix now issues for it (its own
scenario now legitimately diverges too, since the shield Task's write lands before the weapon Task's
own resolution).

### 3. [stage-2, non-blocking — FIXED] Slot→handle mapping was a binary `else`, not exhaustive

**file:** `Packages/elf_Kit/Sources/UILayer/Dev/BattleSetup/BattleSetupViewModel.swift:223-233` (pre-fix)
**AC:** n/a

`itemType == .weapons ? weaponTask : shieldTask` routed *any* non-`.weapons` type onto the shield
handle. A future third validating slot would silently share the shield handle's cancel-and-replace
lifecycle with no compiler warning. The guarding doc comment was also detached from the declaration
(separated by a blank line).

**Fix applied:** both `validationTask(for:on:)` and `setValidationTask(_:for:on:)` now switch
exhaustively over `HeroItemType` with an explicit `default` no-op case; the comment was reattached and
reworded to describe the new defensive default.

### 4. [stage-2, non-blocking — FIXED] Per-slot Task handle was never reset to `nil` on completion

**file:** `Packages/elf_Kit/Sources/UILayer/Dev/BattleSetup/BattleSetupViewModel.swift:208`
**AC:** n/a

`weaponValidationTask`/`shieldValidationTask` were only ever assigned, never cleared on completion —
harmless today (the sole reader is the next selection's `.cancel()`, a no-op on a finished Task) but
left a stale handle retained indefinitely.

**Fix applied:** the Task body now clears its own slot's handle to `nil` at the end, after the merge
write — safe because reaching that point without having been cancelled already proves this Task is
still the slot's current handle (cancellation and replacement happen synchronously together, with no
`await` in between).

### 5. [stage-2, non-blocking — FIXED] `FakeWeaponValidator.waitUntilPending` had no timeout

**file:** `Packages/elf_Kit/Tests/elf_KitTests/Helpers/FakeWeaponValidator.swift:58-63` (pre-fix)
**AC:** n/a

Suspended on an unbounded `CheckedContinuation` — a future regression that stopped calling the
validator on some path would hang the test/CI indefinitely instead of failing readably.

**Fix applied:** `waitUntilPending` now takes a `timeout` (default 2s) and races the continuation
against a cancellable timeout Task that fails the test with a descriptive message and resumes the
continuation itself if the expected call count never arrives.
