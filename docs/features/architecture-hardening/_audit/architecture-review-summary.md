# Elfy — Architecture Review: Flat vs Layered vs Feature Modules

_Дата: 2026-07-09 · Автор: Vitalii Lytvynov_
_Основано на: deep-research (19 источников, 21 подтверждённое утверждение) + скан кодбейса._

---

## TL;DR

**Не переходи ни на «слоёную», ни на «модульную по фичам» архитектуру сейчас. У тебя уже и то, и другое — просто ты называешь это «плоским».** Настоящая боль локализована в 3–4 god-объектах и паре раздувшихся ViewModel, а не в структуре модулей. Лечится точечной хирургией + одним соглашением о папках, а не миграцией архитектуры.

---

## 1. Диагноз: это НЕ flat-архитектура

| Что заявлено | Что показал скан |
|---|---|
| «flat + MVVM, всё в кучах» | Модули разложены **строго направленно** (нет циклов, зависимости текут вниз) |
| «всё вперемешку» | `DataLayer` группируется **по роли → домену → триаде** (`protocol + Implementation/ + Dependencies/`) |
| «трудно найти код» | `Screens` и `UILayer` **уже по-фичевые** (21 экран, 25 фиче-папок VM) |

**Граф зависимостей (уже правильный, менять нечего):**

```
elf.xcodeproj (app)
   ├─► elf_iOS ──► elf_SwiftUI + elf_Kit + swift-dependencies
   ├─► elf_Kit ──► swift-dependencies
   └─► elf_SwiftUI  (лист, без зависимостей)
```

Плоские растущие «кучи» остались лишь местами (крупный домен Combat + несколько отдельных распухших файлов). Проблема **точечная, не системная.**

## 3. Выводы исследования (verified, голосование 3-из-3)

1. **«Правильной» архитектуры нет** — она функция размера команды и сложности. Один разработчик, pet-проект → нижний сегмент, где советуют **не дробить**.
2. **Консенсус — гибрид** (вертикальные фиче-слои поверх горизонтальных Core/Domain/DesignSystem). У Elfy уже так.
3. **«Start coarse» / monolith-first** — дроби только когда появятся реальные границы.
4. **Триггер нового SPM-модуля = ощущаемое трение**, а не число файлов: медленные билды / каскад правок / нельзя открыть preview без всего стека. **Ни один у тебя не сработал.**
5. **Внутри модуля — «Rule of Threes»** (Sundell): группировку «все VM / все Service» перестают масштабировать; 3+ связанных куска → со-локализуй по фиче.
6. **Папки дёшевы и обратимы; граф модулей — load-bearing.** Регруппировку папок делай смело, новый модуль — только с планом миграции.

> Оговорка: источники — практические блоги + open-source книга Cermak. Официальных Apple/Point-Free доков в первоисточниках нет. Это сходящееся best-practice мнение, не эмпирика — но сходимость сильная.

## 4. Рекомендация

### ❌ НЕ делать сейчас
Не выделять фиче-модули SPM (`CombatFeature`, `DungeonFeature`, …). Преждевременно: нет билд-трения, каскадов, команды. Получишь весь налог модуляризации при ~нулевой выгоде.

### ✅ Делать вместо этого

**(A) Хирургия god-объектов — ~80% боли здесь:**
- `GameSession` (564) → вынести `make*ViewModel()` фабрики в отдельный `ViewModelFactory` (или по одной на домен); в сессии оставить только state.
- `DungeonSession` (365) → тот же разрез.
- `BattleFightViewModel` (422) → резать по паттерну Inventory (`+Display`-экстеншены + чистая логика в Formatter/Aggregator).
- Combat-калькуляторы — НЕ трогать ради размера (реальная сложность), только если внутри смешаны ответственности.

**(B) Одно соглашение о папках:**
- Применить Rule of Threes к последним плоским бакетам. Главный кандидат — `elf_SwiftUI/Components/` (20 файлов кучей) → сгруппировать (`Combat/`, `Inventory/`, `Shared/`).
- Зафиксировать в `model-organization.md` / `project-architecture.md`: **3+ файла одной фичи в плоской папке → подпапка по фиче, не по типу.**

**(C) Триггеры будущей модуляризации:**
- Первый кандидат на модуль — **Combat** (крупнейший домен, пронизывает Services/Model/UILayer/Screens). Выделять, если билд `elf_Kit` заметно замедлится или понадобится автобитва-симулятор отдельным таргетом.
- Численные сигналы «распух»: VM/Service > ~250–300 LOC → искать смешанные ответственности; папка > ~15 файлов одного типа → группировать по фиче.

## 5. Tradeoffs

| | **Оставить + хирургия (рекомендация)** | Слои внутри `elf_Kit` | Фиче-модули SPM |
|---|---|---|---|
| Усилие | Низкое, инкрементально | Среднее | Высокое, разовая миграция |
| Решает «трудно найти» | ✅ да | Частично | ✅ да, но избыточно |
| Билд-выигрыш | ~0 (и не нужен) | ~0 | Есть, но незаметен |
| Риск | Минимальный, обратимо | Средний | Высокий, load-bearing |
| Соответствие ресёрчу | ✅ прямое попадание | Допустимо (слои уже есть) | ❌ преждевременно |

---

## Итог

Elfy уже в «правильной» точке: направленный граф из 4 модулей + гибридная группировка по роли/домену. «Flat»-боль — это не архитектура, а 3–4 god-объекта (`GameSession` 564 во главе) и пара плоских бакетов. Раздроби фабрики из сессий, дожми крупные VM приёмом Inventory, введи правило «3+ файла фичи → подпапка» — и «трудно найти код» уйдёт без единого нового `Package.swift`. Модули по фичам держи как запланированное будущее с триггером «Combat + реальное билд-трение».
