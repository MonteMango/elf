## TL;DR

Кодовая база **заметно выше среднего** — по структуре читается как уверенный mid-level
enterprise iOS-проект, а не хобби-пет-проект. Слоистость, DI и моделирование на value-типах
действительно сильные. Проблемы — **не «грязь, которую надо отмыть», а неравномерность**:
отличные паттерны применены где-то и пропущены где-то ещё. Предстоящая работа — *поднять пол
до уровня потолка*, а не переписывать.

| Измерение | Оценка | Одной строкой |
|---|---|---|
| Слоистая архитектура (3 SPM-пакета) | 8 / 10 | Чистое направление зависимостей, UI-агностичное ядро |
| DI (swift-dependencies) | 9 / 10 | Авто-композиция `liveValue`, snapshot-in-init |
| MVVM | 8 / 10 | ViewModels живут в core-пакете, тестируемы headless |
| Модели / value-типы | 8 / 10 | Сильные инварианты, гранулярность, ID-reference persistence |
| Type-driven design | 9 / 10 | `TypedID` теперь сквозной (T-1 ✅); невозможные состояния непредставимы |
| Консистентность | 7 / 10 | ID унифицированы (✅); логирование и обработка ошибок ещё расходятся |
| Покрытие тестами | 7 / 10 | Сильное на боевом ядре, тонкое на слое ViewModel/UI |

## 1. Архитектура

### 1.1 Слоистость пакетов

```
elf_SwiftUI   (design system, button styles, компоненты — без бизнес-логики)
     ▲
elf_Kit       (DataLayer: модели/сервисы/репозитории + UILayer: ViewModels — без SwiftUI-вью)
     ▲
elf_iOS       (Screens/Views + Navigation + Coordinator + DI bootstrap)
```

**Вердикт: сильно.** Направление зависимостей корректное, а выбор границ — осознанный:

- **ViewModels живут в `elf_Kit/UILayer`, а не рядом со вью.** Это выдающееся решение. Оно держит
  ViewModels свободными от SwiftUI, делает их тестируемыми headless и сохраняет core-пакет
  UI-агностичным. Многие команды никогда не доводят это до правильного состояния.
- `elf_SwiftUI` несёт **ноль бизнес-логики** — чисто design system. Это совпадает с правилом из
  CLAUDE.md «все UI-стили живут в design system; не создавать локальные константы стилей в
  `elf_iOS`».

**Ограничение (на будущее, не сейчас): слоистость, а не feature-модульность.** Всё в `elf_Kit` —
один таргет, организованный по *слою* (`DataLayer/`, `UILayer/`). Для solo-проекта сегодня это
правильный выбор. Но когда `elf_Kit` перерастёт ~40–50k LOC, нарезка по слоям начнёт мешать: время
сборки растёт (один таргет пересобирается широко), а границы фич размываются (combat, farming,
crafting, dungeon делят одно пространство имён). Enterprise-альтернатива — **feature-модули**
(`CombatKit`, `FarmKit`, …), каждый со своими внутренними слоями. **Пока этого делать не нужно** —
отметить как exit ramp на случай масштабирования.

### 1.2 Dependency Injection — лучшая часть кодовой базы

Тройка `Protocol + Implementation/ + +Dependency` — образцовый swift-dependencies:

```swift
// SnapshotCombatCalculator.swift — протокол, Sendable, с удобным default
public protocol SnapshotCombatCalculator: Sendable { … }
public extension SnapshotCombatCalculator {
    // резолвит \.withRandomNumberGenerator один раз, затем делегирует
}

// SnapshotCombatCalculator+Dependency.swift — ключ, приватный enum
private enum SnapshotCombatCalculatorKey: DependencyKey {
    static var liveValue: any SnapshotCombatCalculator { ElfSnapshotCombatCalculator() }
}
```

Три вещи позволяют этому масштабироваться до ~170 сервисов без боли:

1. **Авто-композиция.** Каждый `liveValue` резолвит *свои собственные* `@Dependency`, поэтому
   добавление сервиса не требует правки центрального composition root. `DependencyBootstrap.run()`
   связывает только асинхронно загружаемые корневые репозитории; всё остальное самособирается.
2. **Snapshot-in-init** (`BattleFightViewModel.swift:133-152`, `GameSession.swift:52-63`):
   `@Dependency` читается внутри инициализатора и сохраняется в `let`. Это устраняет классический
   баг «зависимость зарезолвлена не в той области видимости» и держит живой объект стабильным.
3. **DI распространяется на хелперы, а не только сервисы** — Builders, Validators, Calculators и
   Resolvers все проходят через `@Dependency` (см. память `feedback_di_for_helpers`). Никогда не
   конструируются напрямую.

### 1.3 Навигация

`AppRoute` (enum) → маппинг `.view()` → `AppCoordinator` (жизненный цикл) → `SessionRouteView`
(инжектит сессию через `@Environment`). Координатор тонкий (66 LOC) и делает *только* жизненный
цикл (start / end / save-on-background). Хорошее разделение.

См. **Finding A-2** — единственная реальная слабость здесь (роуты несут целые доменные модели).

## 3. Подробные находки

### T-1 ✅ — `TypedID` применён обратно пропорционально риску — **РЕШЕНО (2026-06-11)**

**Сделано.** Все продакшен-сущности переведены с сырого `UUID` на фантомно-типизированные id.
Введено 16 новых алиасов: `BuffID`, `AppliedBuffID`, `MonsterID`, `ItemID`, `OwnedItemID`,
`RecipeID`, `DungeonID`, `DungeonRoomID`, `ElfID`, `HouseID`, `GameID`, `GameDayID`,
`PlayerCharacterID`, `CombatantID`, `BattleID`, `MaterialID`. Плюс два sum-типа для гетерогенных
ссылок: `CombatantSource { elf(ElfID) / synthetic / monster(MonsterID) }` (замена
`CombatantSnapshot.sourceId`) и `MaterialRef { fish / herb / ore / monster }` (замена пары
`(id, source)` у `InventoryMaterial`, заодно убраны `.rawValue`-распаковки). Каталог vs
owned-instance теперь различимы на уровне типов (`ItemID` vs `OwnedItemID`). `IDTypes.swift`
раздроблён по фичам (`Catalog/Fish/FishID.swift` и т.д.). Сборка зелёная, 398 тестов проходят,
SwiftLint чист. Формат сейва изменился только для материалов (`ref`) — дев-сейвы вайпнуть.
Остаточные сырые `UUID` — осознанные (собственные instance-id `DuelPair`/`BattleRound`/`DropItem`,
material/ore-ссылки в рецептах/квестах, Dev-модели).

<details><summary>Исходный анализ (история)</summary>

**Что.** Phantom-типизированные ID существуют (`TypedID<Tag>`, `TypedID.swift`) и используются для
**каталожных** сущностей: `FishID`, `HerbID`, `OreID`, `QuestID`, `QuestCharacterID`
(`IDTypes.swift`). Но **runtime / combat** ядро работает на сыром `UUID` — ~190 вхождений:
`playerCombatantId: UUID?`, `leftCombatantId: UUID`, `rightCombatantId: UUID`, `combatantId: UUID`,
`buffId: UUID`, `allyIds: [UUID]`, `sourceId` и т.д. **Нет** ни `ElfID`, ни `MonsterID`, ни
`CombatantID`, ни `BuffID`, ни `DungeonID`.

**Почему важно.** Боевая/buff-система — самая сложная часть приложения *и* самая насыщенная
жонглированием ID — ровно там, где перепутанный UUID компилируется нормально и падает в runtime.
Типобезопасность применили к *низкорисковому* каталогу (fish ID редко путают с herb ID) и
пропустили на *высокорисковом* ядре. Ирония: собственный doc-комментарий `TypedID` использует
`ElfID` и `MonsterID` как примеры — ни одного из них не существует.

**Контекст best-practice.** Это запах «Primitive Obsession» — использование `UUID`/`String`/`Int`
там, где место доменному типу. Phantom-типы превращают целый класс багов «передал не тот id» в
*ошибки компиляции* при нулевой стоимости в runtime. См. `type-driven-design.md` (Make impossible
states unrepresentable).

**Набросок фикса (инкрементально, по одной сущности за раз):**
```swift
// IDTypes.swift
public enum CombatantIDType: IDType {}
public typealias CombatantID = TypedID<CombatantIDType>

// Затем мигрировать по одной модели за раз. Codable уже round-trip-ит как голый UUID,
// поэтому сохранённые сейвы продолжают загружаться (см. Codable-conformance в TypedID.swift).
// Начать с листа (CombatantSnapshot.id) и идти за компилятором.
```
Предлагаемый порядок: `CombatantID` → `DuelPair`/`HeroSelection` → `BuffID` (`AppliedBuff`,
`BuffCatalogID`) → `MonsterID` → `ElfID`. Компилятор ведёт каждый шаг; тесты ловят регрессии.

</details>

### A-1 🟡 — `GameSession` — растущий facade-god-object

**Что.** `GameSession` явно владеет *всей* мутацией уровня игры, by design — его
собственный doc гласит: *«Отдельного слоя сервисов под ним нет — логика мутации живёт прямо в этом
типе»*. Сейчас он охватывает progression, inventory, crafting, buffs, смену дня, жизненный цикл
dungeon, **награды подземелья** и persistence.

**Почему важно.** *Форма*, которая растёт без предела — каждая новая фича добавляет сюда ещё один
метод. Швы уже видны: см. **DUP-1**.

> **Обновление 2026-06-20.** Прогноз подтвердился: фича наград подземелья добавила в `GameSession`
> сразу несколько методов — `finishDungeonRun()`, `bankDungeonRewardsOnDeath()`,
> `discardDungeonRun()`, приватный `flushRewards(from:)` и overload
> `addDropsToPlayerInventory(materials:weapons:armor:)`. Размер вырос **251 → 556 LOC** (×2.2).
> Это ровно тот безлимитный рост, о котором предупреждала находка. Dungeon-run-флаш — первый
> очевидный кандидат на вынос: оркестрацию выхода из похода (flush леджера → release сессии) можно
> увести в тонкий `DungeonRunService`/мутатор, оставив `GameSession` лишь точкой входа.

**Направление фикса.** Оставить `GameSession` как **фасад** (единая точка входа, которой пользуются
вью), но чтобы он *оркестрировал* тонкие мутаторы, а не *реализовывал* их — так же, как он уже
делегирует crafting в `CraftService`, а добавления в inventory в `InventoryService`. Вынести
progression и семейство inventory-add за маленькие сервисы; фасад лишь выстраивает
последовательность вызовов. Цель: `GameSession` оркестрирует, никогда не реализует доменные правила
инлайн.

### A-2 🟡 — Роуты навигации несут целые доменные модели

**Что.** `AppRoute` несёт `Game`, `Battle`, `[GameDay]` по значению
(`AppRoute.swift:18-33`). Поскольку эти payload-ы не дёшево `Hashable`, enum нуждается в
**~72 рукописных строках** `Equatable`/`Hashable` (`AppRoute.swift:38-112`), которые сравнивают
только по `id`.

**Почему важно.**
- Два роута с одинаковым `battle.id`, но разным содержимым считаются *равными* → латентные баги
  навигации при повторном push роута.
- Целый `Battle`/`Game` внутри enum навигации — состояние не в том месте. Канонический паттерн:
  роуты несут **ID**; экран-назначение резолвит сущность из сессии / репозитория. Это удаляет весь
  ручной блок `Hashable` (enum авто-синтезирует его, как только payload-ы становятся `Hashable` ID).

**Набросок фикса:** `.battleFight(BattleID)` + резолв в `BattleFightRouteView`;
`.gameSession(GameID, playTime:)`; `.calendar(currentDayNumber: Int)` (массив календаря уже в
сессии). После T-1 (✅) типы `BattleID`/`GameID`/`DungeonID` уже существуют — `AppRoute.dungeon`
уже несёт `DungeonID` + `[ElfID]`; осталось перевести `.gameSession`/`.battleFight` на id-payload-ы
и удалить ручной `Hashable`/`Equatable`.

### C-1 🟡 — Несогласованность логирования

**Что.** В проекте есть правильные абстракции логирования — `DebugGameLogger`, `DebugBattleLogger`,
с реализациями `Console*` и `NoOp*` за `@Dependency`. И всё же в Sources ~174 сырых вызова `print(`,
а несколько ViewModel логируют голым `print()`, обходя абстракцию:
`CharacterCreationViewModel.swift:201,209,219,222`, `BattleSetupViewModel.swift:323,412`. Некоторые
даже не обёрнуты в `#if DEBUG` (`BattleFightViewModel.swift:403` — обёрнут, что и есть правильная
форма).

**Почему важно.** Шов логирования существует именно для того, чтобы вывод можно было заглушить/
перенаправить в тестах и релизе; обход его через `print()` сводит это на нет и протекает в
release-консоль.

**Фикс.** Направить логирование ViewModel через `@Dependency(\.debugGameLogger)` (или выделенный
`errorReporter`), а сырой `print` оставить только для реализаций логгеров `Console*`. Кастомное
правило SwiftLint может запретить `print(` вне `*/Implementation/*Logger*.swift`.

### E-1 🟡 — Молчаливые сбои сохранения

**Что.** `BattleFightViewModel.applyBattleRewards` делает `try await session.save()` внутри
`do/catch`, который только `print`-ит под DEBUG (`:399-405`). `AppCoordinator.saveIfNeeded`
использует `try? await gameSession?.save()`. Всего по коду 42 использования `try?`.

**Почему важно.** Сбой сохранения = молчаливая потеря прогресса. Для игры это один из худших UX-
провалов, и сейчас он невидим.

**Фикс.** Определить контракт ошибок: показывать неблокирующий баннер/флаг «не удалось сохранить»
во вью и рассмотреть уже отмеченный в TODO debounce/coalesce (`GameSession.swift:227`). Даже просто
`@ObservationIgnored var lastSaveError`, который может читать UI, был бы шагом вперёд.

### B-1 🟢 — Контракт bootstrap через `fatalError`-в-`liveValue`

**Что.** У каждого асинхронно загружаемого каталожного репозитория `liveValue` — это
`fatalError("… must be registered via prepareDependencies at app bootstrap")` (11 из 25
`fatalError`). Приложение гейтит корневой UI за splash-экраном, который ждёт
`DependencyBootstrap.run()`, поэтому на практике это безопасно.

**Почему важно.** Это **контракт упорядочивания только времени выполнения**: любое чтение
`@Dependency(\.fooRepository)` до bootstrap крашит приложение. Это fail-fast (защитимо), но невидимо
для компилятора. Preview или новая точка входа, читающая репозиторий слишком рано, упадёт без
статического предупреждения.

**Варианты.** (a) Оставить, но задокументировать контракт в одном месте (сейчас он повторяется в 11
файлах). (b) Рассмотреть `testValue`/`previewValue`, возвращающий пустой in-memory репозиторий,
чтобы previews/tests не натыкались на живой `fatalError`. Остальные `fatalError`
(`BuffCatalogID.swift:25`, `EquippedItemsSaveData.swift`) — легитимные guard-ы инвариантов старта.

### M-1 🟢 — Идентификация игрока по индексам

`Game` хранит `playerHouseIndex: Int` / `playerMemberIndex: Int` (`Game.swift:30-33`) — позиции в
массиве, а не ID. O(1) и нормально для фиксированного турнира 8×10, но хрупко: любая перестановка
`houses`/`members` молча переуказывает на другого игрока. Собственный `persistence-patterns.md`
проекта предпочитает паттерн ID-reference. Низкий приоритет (форма турнира фиксирована), отмечено
для осведомлённости. Рискованно менять — делать последним, если вообще.

### TEST-1 🟡 — Пробел в тестах ViewModel

23 `@Observable` ViewModel, **1** файл тестов ViewModel (`BattleFightViewModelTests`). Ядро
combat/damage/validator хорошо покрыто (и есть headless balance-sweep integration-таргет — хорошо),

## 4. Что действительно сильно (так и продолжать)

- **Value-типы с инвариантами.** `Attribute` (clamped ≥ 0, `AdditiveArithmetic`,
  `ExpressibleByIntegerLiteral`, кастомный `Codable`), `HitPoints`, `ActionPoints`, `DamageRange`,
  `CharacterName` — невозможные состояния непредставимы. Фабрики `unsafeCreate`/`create` делают
  непроверяемый путь явным.
- **Гранулярные модели.** ~один тип на файл; с 2026-06-11 сгруппированы по роли
  (`ValueTypes/`, `Catalog/`, `RuntimeDomain/`, `Combat/`, `Persistence/`, …). Поиск тривиален.
- **Сквозные типобезопасные id (T-1 ✅).** Все сущности на `TypedID<Tag>` — перепутать id-кинды
  невозможно (ошибка компиляции), при нулевой стоимости в runtime. Гетерогенные ссылки —
  через sum-типы (`CombatantSource`, `MaterialRef`).
- **Persistence-DTO отделены.** 16 типов `*SaveData` держат форму на диске развязанной с runtime-
  моделями (ID-reference). Опирается на политику «никаких миграций в раннюю разработку».
- **Доменные инварианты в конструкторах** (preconditions в `Game.init`: ровно 8 houses).
- **Дисциплина `private(set)`** — публичное чтение, запись только внутри модуля. `GameStore`
  предоставляет read-only состояние; мутация — `internal(set)` внутри `elf_Kit`.
- **Комментарии объясняют *почему*, а не *что*** — например, заметка «не удалять как мёртвый код» на
  точках входа глобальных buff (`GameSession.swift:178-183`), обоснование defensive-fallback
  `?? .draw`, doc про half-up `scaledVital`. Это редко и ценно.
- **Seedable, проброшенный через DI RNG** для боя (см. память `project_rng_architecture`) — делает
  balance-sweeps детерминированными.
- **Очень мало force-unwrap (4 в Sources)** и фактически ноль нарушений правила `static` (весь
  `static` — это `liveValue`, операторы/фабрики или константы).
- **SwiftLint настроен** (`.swiftlint.yml`).

## 5. Сравнение с enterprise-архитектурой

| Аспект | Elfy | Типичный enterprise iOS | Вердикт |
|---|---|---|---|
| Модульность | 3 слоистых пакета | feature-модули + core | Слоисто; норм для solo, см. exit ramp §1.1 |
| DI | swift-dependencies, авто-композиция | Swinject / самописный root / Needle | Elfy **легче и современнее** |
| MVVM | VM свободны от UI, тестируемы | VM часто связаны с UIKit/SwiftUI | Elfy **чище** |
| Навигация | enum-роутер + координатор | Coordinator / RIBs / TCA | Сопоставимо; протекает домен (A-2) |
| Типобезопасность | value-типы + сквозной `TypedID` (T-1 ✅) | редко настолько строго | **Сильно** — id-кинды непредставимо перепутать |
| Обработка ошибок | местами `try?` + `print` | явные пайплайны ошибок / reporting | **Ниже** enterprise (E-1, C-1) |
| Тестирование | сильное ядро, тонко на VM/UI | полная пирамида вкл. UI/snapshot | Ядро сильно; **тонко выше** (TEST-1) |

**Чего не хватает для «полного enterprise»:** feature-модульности (только когда потребует масштаб),
явного контракта обработки ошибок/reporting и UI/integration-тестов над ядром. **Ничего из этого не
стоит гнаться ради самого себя на solo-проекте** — слоистый дизайн здесь уместен. Стоит закрывать
пробелы в обработке ошибок и консистентности, а не в модульности.
